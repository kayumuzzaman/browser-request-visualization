What Happens When

What happens when you type google.com and press Enter?

google.com

One keypress sets off 24 stages across six places: your keyboard, your operating system, your browser, the network, a server, and your browser again. This page follows the request through each one, in order.

Reading level

Place 1 of 6

Keys

The story starts before Enter. Every letter you type is already doing work, and the Enter key itself is a small electrical event.

Keys

The “g” key is pressed

As soon as you type the first letter, the browser starts guessing where you want to go. It offers suggestions in a dropdown under the address bar and narrows them with every further letter.

  • The browser receives the key event and its auto-complete functions run.
  • What you see depends on the browser's algorithm and on whether you are in private or incognito mode.
  • Most algorithms sort and prioritise by search history, bookmarks, cookies, and popular searches from the internet as a whole.
  • Many blocks of code run on each keypress. The browser may suggest “google.com” before you finish typing it.

Keys

The Enter key bottoms out

This is time zero. Pressing Enter closes an electrical circuit. A small chip inside the keyboard notices, cleans up the noisy signal, and turns it into a number that means “Enter”. That number is then sent to the computer.

  1. Power. The keyboard's USB circuitry runs on the 5V supply provided over pin 1 by the computer's USB host controller.
  2. Store. The keycode is held in a register inside the keyboard called the “endpoint”.
  3. Poll. The host USB controller asks that endpoint for its value at the interval the keyboard declares, roughly every 10 ms for a low-speed device.
  4. Packetise. The value goes to the USB SIE (Serial Interface Engine), which converts it into one or more USB packets.
  5. Transmit. The packets travel as a differential electrical signal over the D+ and D− pins (the middle two) at up to 1.5 Mb/s when the keyboard runs as a low-speed device. Keyboards belong to the HID (Human Interface Device) class.
  6. Decode. The host USB controller decodes the signal, the HID universal keyboard driver interprets it, and the key value is passed into the operating system's hardware abstraction layer.
  1. Touch. On a capacitive screen a tiny amount of current transfers to your finger. That completes a circuit through the electrostatic field of the conductive layer and creates a voltage drop at that point. The screen controller raises an interrupt reporting the coordinate.
  2. Press event. The mobile OS tells the focused application that one of its GUI elements was pressed. Here that element is a button of the virtual keyboard.
  3. Key message. The virtual keyboard raises a software interrupt to send a “key pressed” message back to the OS.
  4. Delivery. That interrupt notifies the focused application of a “key pressed” event.
Verified detail
  • A USB keyboard reports Enter as HID usage 0x28. On Windows the keyboard driver turns that into scan code 0x1C, which is then mapped to the virtual-key code VK_RETURN: 0x0D, or 13. That is where the familiar 13 for Enter comes from.
  • Keyboards are not limited to low speed. A low-speed device is polled every 8 ms at best, a full-speed device can be polled every 1 ms, and keyboard firmware such as QMK makes the polling interval a setting.

Sources: USB HID usage table, Microsoft: keyboard input, Microsoft: USB endpoint descriptor, QMK configuration

Place 2 of 6

Operating system

The number has reached the computer. Now the OS has to work out which program should hear about it and deliver the event to the browser's address box.

Operating system

Interrupt fires (not for USB keyboards)

A non-USB keyboard taps the processor on the shoulder. The processor stops what it is doing, looks up which piece of operating-system code handles this kind of tap, and runs it.

Verified detail

A USB device cannot start an interrupt transfer by itself. It queues its data and must wait until the host polls it.

Sources: USB in a NutShell

Operating system

The OS hands the key to the browser

The OS turns the raw signal into a “key down” event and drops it into the queue of whichever window is in front. Each operating system has its own chain of drivers and messages for this.

  • KBDHID.sys is the HID mapper driver for keyboards. KBDCLASS.sys is the keyboard class driver that serves every keyboard and keypad on the system.
  • lParam packs more about the keystroke: the repeat count, the scan code, an extended-key flag and a few state bits.
  • The message waits in the thread's queue until the window's message loop retrieves it and hands it to the window procedure, its WindowProc.
  • The address box is an edit control. Its WindowProc has a handler for WM_KEYDOWN that looks at wParam, sees VK_RETURN, and knows the user pressed Enter.
Verified detail
  • Windows. VK_RETURN (0x0D) is a virtual-key code, which names what a key means. A scan code names the physical key, and Enter's is 0x1C. Keyboard messages are posted to the message queue of the thread that owns the focused window.
  • macOS. The path shown follows Apple's event architecture guide. The system was called OS X until 2016.
  • GNU/Linux. The X server delivers key events to client windows itself. Wayland is replacing Xorg: in 2025 GNOME 49, Fedora 43 and Ubuntu 25.10 were announced as Wayland-only for GNOME.

Sources: Microsoft: virtual-key codes, Microsoft: keyboard input, Microsoft: HID client drivers, Apple: event architecture, Engadget, Xlib manual, Fedora: key processing, The Register

Place 3 of 6

Browser decides

The browser now knows you pressed Enter on the text “google.com”. Before anything leaves your machine it has four questions to settle.

Browser decides

Parse the URL

You typed only a name. The browser fills in the missing pieces to make a complete address: which protocol to speak and which page to ask for.

Browser decides

Is it a URL or a search term?

The address bar doubles as a search box, so the browser has to decide which one you meant.

Browser decides

Convert non-ASCII characters in the hostname

The naming system of the internet only understands a small alphabet. If a hostname contains anything else, the browser rewrites it into that alphabet first.

Verified detail

The encoded form of münchen.de in the figure was computed, not copied.

Browser decides

Check the HSTS list

The browser ships with a list of sites that have asked never to be contacted without encryption. If the site is on it, the browser uses HTTPS straight away.

Verified detail
  • Chrome's address bar has used https:// by default since version 90 (2021), falling back to HTTP only when the HTTPS attempt fails.
  • Since Chrome 154 (stable on 22 September 2026) Chrome asks before loading a public site over plain HTTP.
  • Firefox 136 and later also try HTTPS first and fall back to HTTP if that fails.
  • For google.com the HTTPS attempt succeeds, so in these browsers the plain-HTTP request never happens.

Place 4 of 6

Network

The longest stretch. The browser must find the server's number, find a way out of the local network, open a reliable connection, encrypt it, and finally ask for the page.

Network

DNS lookup

Computers reach each other by number (an IP address), and “google.com” is only a name. DNS is the lookup that turns one into the other. The browser checks the nearest notebooks first and only asks over the network if none of them has the answer.

Verified detail
  • Chrome's net-internals page no longer lists the cached entries. It has a lookup form and a “Clear host cache” button. A network log export shows the cache contents.
  • getaddrinfo replaced the older gethostbyname, which is obsolete and was removed from POSIX in 2008.
  • Browsers can skip the OS lookup. Chrome switches to DNS over HTTPS when your DNS provider supports it (since version 83), and Firefox uses DNS over HTTPS by default in some countries.

Sources: Chromium source, Chromium's DNS cache, gethostbyname(3), Chromium Blog: Secure DNS, Mozilla: DNS over HTTPS

Network

ARP process

Inside a local network, data is delivered to hardware addresses (MAC addresses). Your computer knows the IP address it wants to reach but not the hardware address behind it. ARP is shouting “who has this IP?” to the whole room and waiting for the owner to reply.

The router receives the request and responds with an ARP reply.

The hub broadcasts the ARP request out of all its other ports. If the router is on the same “wire”, it responds with an ARP reply.

The request is a broadcast frame, so the switch sends it out of every port except the one it arrived on. The router answers with an ARP reply addressed to your computer alone, and the switch uses its MAC address table (also called a CAM table) to forward that reply out of the right port.

Verified detail
  • ARP supplies a hardware (MAC) address. The IP address was already known.
  • The ARP standard lets the sender put the broadcast address in the Target MAC field, as shown, but does not require any particular value there, since it is the value being asked for. What makes the request a broadcast is the destination address of the Ethernet frame that carries it.
  • A switch floods a broadcast frame without reading the ARP contents. Its address table is used for the unicast reply.
  • A recursive resolver asks a root server, which refers it to the .com servers, which refer it to the domain's own name servers.

Sources: RFC 826, Practical Networking, Cloudflare: What is DNS?

Network

Opening of a socket

The browser now has a number to call. It asks the OS for a connection, and the request is wrapped three times on its way out. Each wrapper carries the address that the next handler along the route needs.

  • The browser takes the IP address and the port from the URL (HTTP defaults to port 80, HTTPS to 443) and calls the system library function socket, requesting a TCP socket stream: AF_INET/AF_INET6 and SOCK_STREAM.
  • The source port is chosen from the kernel's dynamic port range (ip_local_port_range in Linux).
  • The packet is then ready to be transmitted over Ethernet, WiFi, or a cellular data network.

Network

The trip across the internet

The packet is passed from router to router, each one reading the destination address and choosing the next hop. A counter in the packet drops by one at every router so that a lost packet cannot circle forever.

  • Modem stands for MOdulator/DEModulator. A second modem at the other end converts the analog signal back into digital data for the next network node.
  • Most larger businesses and some newer homes have fiber or direct Ethernet connections. There the data stays digital and goes straight to the next network node.
  • Each router extracts the destination address from the IP header and routes the packet to the appropriate next hop. The time to live (TTL) field is decremented by one for each router it passes.
Verified detail

The TTL field sets the maximum time a datagram may stay in the internet system. A datagram whose TTL reaches zero must be destroyed.

Sources: RFC 791

Network

The TCP connection flow

Before any real data moves, the two sides agree on how they will count bytes. That takes three messages, often called the three-way handshake. From then on, every byte sent is numbered and every byte received is acknowledged.

Verified detail

The acknowledgment number is the next sequence number the sender of the ACK expects to receive, one past the last byte it has.

Sources: RFC 9293 §3.1

Network

TLS handshake

The connection is reliable but anyone on the route could read it. TLS fixes that. The server proves who it is with a certificate, and the two sides agree on a secret key that only they know. Everything after that is encrypted with the key.

Verified detail
  • TLS 1.3 (2018) removed static RSA key exchange and compression, encrypts every handshake message after ServerHello, and completes a full handshake in one round trip.
  • A 2026 standard, RFC 10024, adds hybrid key exchanges for TLS 1.3 that combine elliptic-curve Diffie-Hellman with the post-quantum ML-KEM algorithm.

Sources: RFC 8446, RFC 10024

Network

If a packet is dropped

Networks get congested and hardware is flaky, so some packets never arrive. The sender reacts by controlling how much it sends at once. It starts small, speeds up quickly, then cautiously, and backs off when something is lost.

  • The algorithm is called TCP congestion control and varies by sender. CUBIC is the default in the Linux, Windows and Apple network stacks. Reno is the classic design, and the chart follows it.
  • The sender chooses a congestion window based on the maximum segment size (MSS) of the connection.
  • In slow start the window grows by at most one segment for each acknowledgment, which roughly doubles it every round trip, until it reaches the slow-start threshold.
  • After the threshold, the window grows by about one segment per round trip.
Verified detail

On a loss, standard TCP sets the threshold to half of the data in flight. CUBIC sets it to 0.7 times the data in flight and cuts the window to match.

Sources: RFC 9438, RFC 5681 §3.1

Network

HTTP protocol

Now the browser can ask its question. An HTTP request is a few lines of plain text: what it wants, from which site, and some extra information. The server replies with a status line, its own extra information, and then the page itself.

  • The text form shown here is HTTP/1.1. Browsers use HTTP/2 or HTTP/3 when the server supports them. Both carry the same requests and responses in binary frames.
  • Older versions (HTTP/1.0, HTTP/0.9) may not include the Host header.
  • HTTP/1.1 applications that do not support persistent connections must include the “close” connection option in every message.
Verified detail
  • HTTP/3 runs over QUIC, which uses UDP and combines the transport and TLS handshakes of stages 13 and 14 into one. About 41% of websites used HTTP/3 in October 2026.
  • SPDY, Google's earlier protocol, was removed from Chrome in version 51 (2016) once HTTP/2 was widely supported.
  • ETag is a response header. The browser sends the saved value back in If-None-Match, and an unchanged page is answered with 304.
  • A request to http://google.com on 8 Oct 2026 returned 301 Moved Permanently pointing to www.google.com, so the page arrives on a later request.

Sources: RFC 9113, RFC 9114, RFC 9000, W3Techs, Chrome 51 removals, RFC 9112 §4, RFC 9110 §13.1.2,

Server

On the other side, a program has been waiting for exactly this kind of message.

Server

HTTP server request handling

The web server reads the request, checks that it is allowed, works out which file or program should answer it, and streams the result back. This stage shows a generic web server. Common ones are Apache and nginx on Linux and IIS on Windows.

Verified detail

Google does not use this generic setup. Its services sit behind the Google Front End, which terminates TLS and acts as a reverse proxy, and a request on 8 Oct 2026 was answered by a server naming itself gws.

Place 6 of 6

Browser draws

The response is back. What arrived is text. Two jobs remain: parsing (HTML, CSS, JS) and rendering (construct the DOM tree → render tree → layout of the render tree → painting the render tree).

Browser draws

Inside the browser

A browser is several programs working together. Knowing the parts makes the remaining stages easier to follow, because the page is handed from one part to the next.

  • The browser's job is to present the web resource you choose by requesting it from the server and displaying it in the window. The resource is usually an HTML document but may be a PDF, an image, or another type of content.
  • Its location is specified with a URI (Uniform Resource Identifier).
  • How HTML files are interpreted and displayed is specified in the HTML standard, maintained by WHATWG, and the CSS specifications, maintained by the W3C (World Wide Web Consortium).
Verified detail
  • Under a 2019 agreement, WHATWG maintains the HTML and DOM Living Standards, and the W3C works in the same repositories and turns review drafts into its Recommendations.
  • Web SQL, once part of browser storage, was removed from Chromium in version 119 and from WebKit in 2019. Firefox never implemented it.
  • This seven-part model comes from the 2011 article “How browsers work”. Its publisher now warns that much of the article is no longer accurate, so read stages 18 to 21 as a simplified model.

Sources: W3C announcement, Chrome: Web SQL timeline, How browsers work

Browser draws

HTML parsing

The rendering engine reads the HTML text and builds a tree out of it, where each tag becomes a node that contains the tags inside it. This tree is the DOM, and it is what scripts and styles work on from here.

  • The rendering engine gets the document's contents from the networking layer, usually in 8kB chunks.
  • The output “parse tree” is a tree of DOM element and attribute nodes. DOM is short for Document Object Model: the object presentation of the HTML document and the interface of HTML elements to the outside world, such as JavaScript.
  • Before any scripting, the DOM has an almost one-to-one relation to the markup.

Why HTML needs its own parser

  • The language is forgiving.
  • Browsers traditionally tolerate well-known cases of invalid HTML.
  • Parsing is reentrant. Script elements containing document.write() calls can add extra tokens, so parsing changes its own input.

There is never an “Invalid Syntax” error on an HTML page. Browsers fix any invalid content and go on.

During and after parsing

  • While the main parser works, a lightweight second parser called the preload scanner reads ahead and starts fetching linked resources: CSS, images, JavaScript files and so on.
  • When parsing is finished, the browser marks the document as interactive and starts parsing scripts in “deferred” mode, those meant to run after the document is parsed.
  • The document state is then set to “complete” and a “load” event is fired.
Verified detail
  • The preload scanner can keep fetching even while the main parser is blocked by a script or stylesheet.
  • The tree in the figure was checked by parsing the snippet in a real browser.

Sources: web.dev: preload scanner, How browsers work,

Browser draws

CSS interpretation

The tree says what is on the page. CSS says how it should look. The browser collects style rules from three places and turns each stylesheet into an object it can query.

  • A CSS parser can be top-down or bottom-up when a specific parser generator is used.

Browser draws

Page rendering

Now the browser combines structure and style, works out the exact size and position of every box, draws the boxes onto separate layers, and stacks those layers into the final picture.

  • The render tree is also called the frame tree.
  • Layout gets more complicated when elements are floated, positioned absolutely or relatively, or use other complex features.
  • Each frame/render object is assigned to a layer, and textures are allocated for each layer of the page.
  • Painting may be rasterized by the CPU or drawn directly on the GPU.
  • All of these steps may reuse values calculated the last time the page was rendered, so incremental changes need less work.
  • The page layers go to the compositing process, where they are combined with layers for other visible content such as the browser chrome, iframes and addon panels.
  • Final layer positions are computed and the composite commands are issued through the platform's graphics API, such as Direct3D, Metal, Vulkan or OpenGL. The GPU command buffers are flushed to the GPU for asynchronous rendering and the frame is sent to the window server.
Verified detail
  • Which graphics API is used depends on the platform and changes over time. Chrome's Skia Graphite backend, launched on Apple Silicon Macs in July 2025, replaces an OpenGL-centred one and draws through Metal, Vulkan and Direct3D by way of the Dawn library.
  • In layout, a box takes its width from its container and its height from its children, which is why the width passes run first.

Sources: Chromium: Skia Graphite, How browsers work

Browser draws

GPU rendering

Drawing involves a huge number of small, similar calculations. A graphics processor is built to do thousands of those at the same time, so the browser can hand the work to it.

Browser draws

Window server

The browser hands its finished frame to the operating system's window system, which combines it with every other window on screen and sends the result to the display.

Verified detail
  • Windows. The Desktop Window Manager has each window draw to an off-screen surface, then renders those surfaces into a desktop image and presents it on the display.
  • macOS. Apple's documentation calls this component the window server.
  • GNU/Linux. On Wayland the compositor is the display server: it combines the buffers of all clients into the final screen image. Under X, the X server sits between the apps and a separate compositor.

Sources: Microsoft: Desktop Window Manager, Apple: event architecture, Wayland architecture

Browser draws

Post-rendering and user-induced execution

The page is on screen, and it keeps working. Scripts run when a timer fires or when you interact, and each run can start the earlier stages again.

Verified detail

Browser plugins such as Flash and Java applets once ran at this stage too. Adobe stopped supporting Flash Player on 31 December 2020 and blocked Flash content from 12 January 2021. Oracle deprecated the Java browser plugin in JDK 9 because browser vendors were dropping the plugin technology it needs.

Sources: Adobe, Oracle

The Google homepage is on your screen.

One key press crossed six places and 24 stages. Much of the trip repeats: every image, stylesheet and script on the page goes through the network stages again, and every script that runs can start another round of layout and paint.
